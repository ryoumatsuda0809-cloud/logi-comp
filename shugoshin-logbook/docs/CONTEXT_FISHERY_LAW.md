# 水産流通適正化法 対応仕様

> **対象**: 水産物情報入力（漁獲番号・品目・重量）の設計判断と法令の根拠
> **最終更新**: 2026-07-28
> **ステータス**: 設計確定・実装前。未解決の照会事項あり（後述）

取適法（待機料）については `CONTEXT_LEGAL_SPEC.md` を参照。本ドキュメントは
水産流通適正化法（特定水産動植物等の国内流通の適正化等に関する法律）側を扱う。

## 1. 法令の要点

### 1-1. 漁獲番号は「構造を持つ16桁」

漁獲番号は乱数ではなく、次の3ブロックの連結である。

```
届出番号(7桁) + 譲渡日 YYMMDD(6桁) + ロット番号(3桁) = 16桁
```

**設計上の含意**: 13桁はアプリ側で自動生成できる。届出番号は荷主ごとに固定、
譲渡日はアプリが保持している。ドライバーが実際に入力すべきはロット番号3桁のみ。

### 1-2. 対象魚種は限定的

| 区分 | 魚種 | 適用開始 |
|------|------|---------|
| 第一種 | アワビ | 2022-12 |
| 第一種 | ナマコ | 2022-12 |
| 第一種 | シラスウナギ（全長13cm以下のウナギ） | 2025-12 |
| 第一種 | 太平洋クロマグロ **大型魚（30kg以上）** | 2026-04 |
| 第二種（輸入） | サバ、サンマ、マイワシ、イカ | — |

**設計上の含意**:
- **フグ・タイは対象外**。下関でフグ中心の運行なら、漁獲番号は大半の運行で不要。
- 太平洋クロマグロは**重量条件（30kg以上）付き**のため、魚種だけでなく
  `weight_kg` と組み合わせて対象判定する必要がある。
- 対象魚種は法改正で追加される（2025-12、2026-04と実際に追加された）。
  魚種リストには**適用開始日を持たせ、日付で有効判定する**こと。

## 2. 設計判断（2026-07-28 決定）

### 決定1: 届出番号(7桁)は `facilities` に保存する

施設ごとに固定値として持つ（`facilities.notification_number` を追加）。
打刻時点で施設は `get_nearest_facility` により特定済みのため、追加の選択操作なしで
自動補完できる。

**前提**: 市場（施設）と荷主が実質1対1であること。1施設に複数荷主が存在すると
判明した場合は荷主マスタへ切り出す（未解決事項3を参照）。

### 決定2: 構造検証に失敗しても記録は許可する（警告のみ）

入力された番号が「登録済み届出番号 + 当日日付 + 3桁」の構造と一致しない場合、
警告を表示するが保存はブロックしない。

**理由**: ドライバーは荷主が発行した番号を転記しているだけで、番号を修正する権限がない。
例外的な番号形式で作業完了できなくなると業務が止まる。過去に
`complete_ticket` のバグでドライバーが恒久的に詰む事故が実際に起きており
（`PROGRESS_LOG.md` 参照）、業務停止リスクの方を重く見る。

### 決定3: 今回のスコープは「構造分解 + 魚種条件表示」まで

- 16桁の単一入力欄をやめ、ロット番号3桁のみの入力にする
- 対象魚種を選んだときだけ漁獲番号欄を表示する（フグ等では欄自体を出さない）

**次フェーズ候補（今回は含めない）**:
- 発注データ（`transport_orders`）からの事前流し込み → 現場入力ゼロ化
- ちょいメモ（音声）→ 待機理由・附帯作業の記録。取適法の証拠強化
- AI-OCR / QR読取 → 伝票の現物確認後に判断

## 3. 設計原則

### 3-1. 打刻の主経路は通信なしで完了できること

市場・港湾は電波状況が悪い。打刻できない＝待機の証拠が残らない＝請求できない、
という法的証拠上の穴になる。

このため入力方式の選定では**オフラインで動くことを優先する**。
構造分解（3桁入力）は電波ゼロでも動くが、AI-OCRは Edge Function 経由で
外部APIを呼ぶため確実に失敗する。通信必須の入力手段を主経路に置かない。

### 3-2. 補足情報を請求計算に混ぜない

将来ちょいメモ等を追加する場合、それらは `wait_log` への補足として保存し、
待機料の計算には使わない。署名済みエビデンスと競合する「第二の真実」を作らない。

### 3-3. AI-OCRを漁獲番号に使う場合は確認を必須にする

16文字の英数字IDは、文字あたり99.5%の精度でも通しで約92%（12回に1回誤読）。
誤読された漁獲番号は「番号なし」より危険で、別ロットを指す偽の法的記録になる。
OCRは下書き生成に留め、ドライバーの確認を経てから保存する。

なお**構造分解を先にやると他の手段が全部楽になる**。読取対象が3桁に減り、
先頭13桁は登録済みの届出番号＋日付と照合できるため、誤読を機械的に検出できる。

## 4. 未解決の照会事項

| # | 内容 | 確認先 | 影響 |
|---|------|--------|------|
| 1 | **貨物自動車運送事業者が「取扱事業者」に該当するか**（運送のみの場合の届出義務） | 水産庁 / 山口県水産部門 | 漁獲番号が法的義務か、荷主向けサービスかが決まる。**最重要** |
| 2 | 伝票の現物（バーコード/QRの有無、番号の印字形式、ロット番号の位置） | 現場で1枚撮影 | OCR/QR採用の可否 |
| 3 | 届出番号は荷主ごとに固定か。1施設に複数荷主がいるか | 荷主ヒアリング | 決定1のデータモデルが変わる |
| 4 | ロット番号は誰が採番し、ドライバーは伝票以外で知り得るか | 荷主ヒアリング | 3桁入力すら不要にできる可能性 |
| 5 | 実運行の魚種構成（対象種の割合） | 運行実績 | ほぼゼロなら設計の重心が変わる |

**#1の回答は書面で取得し、本ドキュメントに追記すること**（法適合アプリの根拠として保存）。
#2〜4は伝票1枚＋荷主ヒアリングでまとめて解決できる。
